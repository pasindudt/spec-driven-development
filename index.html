The Problem

Vibe coding vs. Agentic Engineering

Vibe coding gets you to a prototype quickly. Without specs, that speed compounds into technical debt as systems grow. Here's what separates intuition-driven hacks from production-grade agentic systems.

Origins & Attribution

"Vibe coding" was coined by Andrej Karpathy on 2 February 2025 to describe fully delegating coding to AI — accepting the output without reading, reviewing, or reasoning about the generated code. "Spec-Driven Development" as an AI-era discipline is most associated with Sean Grove's The New Code talk (AI Engineer World's Fair 2025), GitHub's Spec Kit launch (August 2025), and Amazon's Kiro IDE.

Vibe Coding 🎲 Feels productive
  • 🎯 No spec — behavior is defined by whatever the code produces
  • 🌀 Requirements live inside one developer's head
  • 💥 AI agents hallucinate missing context and fill gaps wrong
  • 🔁 Every change risks breaking unknown side effects
  • 🤐 Impossible to hand off or scale to a team
  • 🕳️ No contract between intent, implementation, and test
Prompt to AI
"add a withdrawFunds function that moves money out of a user's account."
↓ AI output
// AI filled every gap by guessing async function withdrawFunds(userId, amount) { const account = await db.getAccount(userId); account.balance -= amount; // no negative-balance check await db.save(account); // no transaction — race condition return { ok: true }; // no error cases }
Spec Driven Dev ⚡ Actually engineered
  • 📄 Behavior is written as a machine-readable spec first
  • 🤖 Agents receive unambiguous context — no guessing
  • 🔗 Every component has a contract: inputs, outputs, invariants
  • 🧭 Change is predictable — the spec is the ground truth
  • 📦 Reproducible across any agent, team, or time
  • ✅ Tests are derived directly from the spec
Spec (written first)
# spec: withdraw-funds.yaml function: withdrawFunds inputs: - name: accountId type: UUID - name: amount type: Money min: 0.01 invariants: - account.balance >= amount - account.frozen === false - operation is atomic outputs: - receipt: TransactionReceipt errors: - InsufficientFunds | AccountFrozen
↓ AI output
// Generated from spec — no guessing async function withdrawFunds({ accountId, amount }) { assert(amount >= 0.01); return await db.transaction(async (tx) => { const account = await tx.lockAccount(accountId); if (account.frozen) throw new AccountFrozen(); if (account.balance < amount) throw new InsufficientFunds(); account.balance -= amount; return await tx.saveReceipt(account, amount); }); // type: TransactionReceipt ✓ }

# spec/auth/login.yaml # Spec Driven Development — Login Feature feature: user-login version: "1.2.0" owner: auth-team status: approved inputs: - name: email type: string format: email required: true - name: password type: string minLength: 12 required: true outputs: success: status: 200 body: AuthToken failure: invalid_credentials: { status: 401, code: "AUTH_001" } invalid_input: { status: 422, code: "AUTH_002" } rate_limited: { status: 429, code: "AUTH_003" } invariants: - password MUST NOT be stored in plaintext - failed attempts MUST be rate-limited after 5 tries per minute - token expiry MUST be ≤ 1h # OWASP recommends ≤ 15–60 min for access tokens - response time MUST be < 400ms at p95 side_effects: - emit: auth.login.success (on success) - emit: auth.login.failed (on failure) - write: audit_log table
# Feature Spec: User Login Version: 1.2.0 | Status: Approved | Owner: auth-team ## Purpose Authenticate a registered user with email + password and return a short-lived JWT. All auth events are audited. ## Inputs | Field | Type | Rules | |----------|--------|--------------------------------| | email | string | required, valid email format | | password | string | required, min 12 chars | ## Success Response — 200 { token: string (JWT), expiresAt: ISO8601 } ## Error Responses | Code | Status | Trigger | |----------|--------|--------------------------| | AUTH_001 | 401 | Wrong email or password | | AUTH_002 | 422 | Malformed input | | AUTH_003 | 429 | >5 failed attempts / min | ## Invariants (MUST hold at all times) - [ ] Passwords stored as bcrypt hash (cost ≥ 12) - [ ] Failed attempts rate-limited after 5 tries / minute - [ ] Token TTL ≤ 1 hour (OWASP recommends ≤ 15–60 min for access tokens) - [ ] p95 response time < 400ms ## Side Effects - Emit auth.login.success or auth.login.failed event - Write row to audit_log table on every attempt
// spec/auth/login.contract.ts // TypeScript contract — machine-readable, type-safe spec interface LoginInput { email: Email; // validated email string password: MinLen<12>; // minimum 12 characters } type LoginOutput = | { status: 200; token: JWT; expiresAt: ISODate } | { status: 401; code: "AUTH_001" } | { status: 422; code: "AUTH_002"; fields: string[] } | { status: 429; code: "AUTH_003"; retryAfter: number }; const LoginSpec = { invariants: [ "password stored as bcrypt, cost >= 12", "rate limit: 5 failed attempts per minute", "token TTL <= 3600 seconds", // OWASP recommends ≤ 15–60 min; adjust per policy "p95 response time < 400ms", ], sideEffects: [ "emit: auth.login.success | auth.login.failed", "write: audit_log (every attempt)", ], } as const; // Agent receives this contract → generates tests → implements export type { LoginInput, LoginOutput }; export { LoginSpec };
Tooling & Methods

How teams make SDD real

Every tool below maps to the same five-stage loop. The tools differ in how much they automate each stage.

The SDD loop — five stages, every feature
1 · Clarify → 2 · Spec → 3 · Tests → 4 · Implement → 5 · Verify

Don't skip stage 1. Most spec bugs are unanswered clarification questions in disguise.

Worked Example

Adding a password reset endpoint — step by step

A concrete walkthrough using real tools. The tools vary — the five stages don't.

1
Clarify — interrogate the requirement before writing anything

Before you open a spec file, resolve every ambiguity: Who triggers the reset — the user, an admin, or both? What is the token TTL? If a user requests two resets in a row, does the first token expire immediately? What happens when an expired token is used? Each unanswered question is a future production bug.

# With Pocock's /grill-with-docs skill (Claude Code): You: "Add a password reset flow to the auth service" Agent: Challenges assumptions, surfaces unanswered questions — token TTL? email vs. SMS? concurrent reset handling? — and documents decisions in ADRs before any spec is written. # With BMAD Analyst agent: You: Describe the feature in plain text Agent: Outputs a PRD with acceptance criteria you must sign off before proceeding
2
Spec — define what the system must do, not how

Write inputs, outputs, error codes, invariants, and side effects. This is the contract. Every downstream step — tests, implementation, code review — is measured against it. If it's not in the spec, you cannot assume it's implemented correctly.

# GitHub Spec Kit (slash command inside your agent): /speckit.specify describe the feature in plain text → agent creates the feature directory and spec.md with a structured template to fill in # one-time project setup: uvx --from git+https://github.com/github/spec-kit.git specify init <PROJECT> # Kiro IDE: Describe the feature in plain text → Kiro drafts requirements + design doc → you review and approve before any agent starts writing code # Manual (works with any agent): Create specs/password-reset.yaml with inputs, outputs, invariants, side_effects → see the YAML format in Spec Examples above
3
Tests — derive them from the spec, not from the code

Each invariant becomes a test assertion. Each error code becomes a test scenario. Tests written from the spec catch intent violations — not just implementation bugs. A test suite generated from the code will only verify what the code already does.

# Pass the spec to your coding agent: "Read specs/password-reset.yaml. Write a test suite that covers every invariant and every error case. Tests should fail until the endpoint exists." # With Pocock's /tdd skill (Claude Code): Agent writes failing tests first. It will not write implementation code until the tests exist. # With BMAD QA agent: Reads the spec → generates a full test plan → hands off to the Developer agent
4
Implement — give the agent the spec and the failing tests

The agent has unambiguous context: a spec that defines behavior and tests that define done. It knows exactly what to build and cannot fill missing requirements with guesses. The spec eliminates the class of bugs that come from agents making reasonable-sounding but wrong assumptions.

# Prompt your coding agent (Claude Code, Copilot, etc.): "Implement POST /auth/reset-password. Spec: specs/password-reset.yaml Tests: tests/password-reset.test.ts — all must pass." # GitHub Spec Kit (slash commands inside your agent): /speckit.plan → generates plan.md and interface contracts /speckit.tasks → parses design docs into a dependency-ordered tasks.md; run each task through your agent # Kiro IDE: Click "Implement" → agents work through the task list, checking each task against the spec
5
Verify — failures name which invariant was violated, not just "something broke"

Run the tests. A red test tells you which invariant is broken and what correct behavior looks like. If the spec was wrong, update the spec first — then tests, then code. If the code was wrong, fix the code. Either way you know exactly what to change and why.

# CI gate (any stack): Block merges when spec and implementation diverge — spec drift becomes a build failure. # Pocock's /diagnose skill: Paste the failing test + the spec → agent traces the failure back to the violated invariant. # Kiro spec hooks: Watch the codebase in real time and alert when a code change breaks a spec invariant.
Tools and frameworks
BMAD Method
workflowmulti-agentagile
A framework where each development phase is handled by a specialized agent with a defined role: Analyst, Architect, PM, Developer, QA.
  • Stage 1–2: Analyst agent turns a brief into a PRD; Architect produces a technical design doc
  • Stage 3–4: PM agent generates spec files and tasks; Developer agent implements against them
  • Stage 5: QA agent verifies implementation against spec acceptance criteria
  • Best for teams who want a fully guided, end-to-end workflow with explicit agent roles
Repo Docs
Matt Pocock's Agent Skills
skillsTDDlightweight
A set of slash commands you add to Claude Code that enforce spec-first discipline at each stage. Composable — use only what your team needs.
  • /grill-with-docs: paste a requirement → agent challenges assumptions and documents decisions in ADRs
  • /tdd: agent writes failing tests before implementation; refuses to code otherwise
  • /diagnose: structured debugging loop that traces failures back to root cause
  • Best for developers who want discipline without adopting a full framework
Repo
GitHub Spec Kit
slash commandspipelineopen-source
A toolkit that installs agent slash commands into your project, enforcing the spec-first pipeline at each stage. Works with 30+ AI coding agents.
  • /speckit.specify: creates the feature directory and spec.md template to fill in
  • /speckit.plan: generates plan.md, data-model.md, and interface contracts from the spec
  • /speckit.tasks: parses design docs into a dependency-ordered tasks.md; pass each task to your agent
  • /speckit.constitution: one-time project setup — establishes non-negotiable constraints and conventions
  • Best for teams who want a structured, agent-native spec pipeline with CI integration
Repo Agent skills extension (community)
Amazon Kiro
IDEspec-firstcommercial
A VS Code-based IDE where specs are first-class project artifacts. Agents cannot start implementation until you review and approve the spec. Review Amazon's data handling policy before using with proprietary code.
  • Stage 1–2: describe in plain text → Kiro generates requirements + design doc for your review
  • Stage 3–4: approve the spec → agents implement against the task list
  • Stage 5: spec hooks watch your code in real time and alert when a change violates a spec invariant
  • Best for teams who want the full spec-first loop baked into the IDE
Website Blog
OpenSpec
brownfieldincrementalopen-sourceactive
A lightweight spec framework designed to work with existing codebases. New changes are described as delta specs — what's changing, not a full restatement of the whole system.
  • Add a spec layer on top of an existing project without rewriting it from scratch
  • Delta specs describe only what is changing for a given feature; the rest of the codebase is treated as stable context
  • Supports 21 agent tools; available as an npm package
  • Best for teams adopting SDD incrementally on an existing system
Repo
Superpowers (obra / Jesse Vincent)
subagentsTDDgates
A methodology with auto-triggered skills and mandatory review checkpoints. Agents cannot proceed past a gate without explicit sign-off.
  • Write spec/design doc → triggers spec review gate; you must approve before agents run
  • Auto-triggered TDD skill enforces tests-first — no implementation without passing tests
  • Subagents handle implementation in parallel; each milestone requires human review
  • Best for long autonomous runs where strong guardrails matter more than speed
Repo
No framework? Start with one rule and one file
manualincremental
You don't need a framework to start practicing SDD. Pick one rule: the agent doesn't write code until a spec file exists.
  • Week 1: Create a specs/ directory. Before your next feature, write a spec in YAML or Markdown (use the format from Spec Examples above). Pass it to your agent instead of a plain English description. Observe what changes.
  • Week 2: Add a second rule: agent generates tests from the spec before writing any implementation. No tests, no code.
  • Week 3: Add a CI check that fails if a new feature directory has no corresponding spec file in specs/.
  • Week 4+: Add traceability — every PR description links to the spec line that motivated each change. Review spec diffs as seriously as code diffs.
