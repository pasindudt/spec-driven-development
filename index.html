The Problem

Vibe coding vs. Agentic Engineering

Vibe coding gets you started fast. It gets you stuck faster. Here's what separates intuition-driven hacks from production-grade agentic systems.

Vibe Coding 🎲 Feels productive
  • 🎯 "It works on my machine" is the only spec
  • 🌀 Requirements live inside one developer's head
  • 💥 AI agents hallucinate missing context and fill gaps wrong
  • 🔁 Every change risks breaking unknown side effects
  • 🤐 Impossible to hand off or scale to a team
  • 🕳️ No contract between intent, implementation, and test
// Vibe-coded function function processOrder(data) { // TODO: validate maybe? const result = doStuff(data); // seems to work ¯\_(ツ)_/¯ return result; }
Spec Driven Dev ⚡ Actually engineered
  • 📄 Behavior is written as a machine-readable spec first
  • 🤖 Agents receive unambiguous context — no guessing
  • ✅ Tests are derived directly from the spec
  • 🔗 Every component has a contract: inputs, outputs, invariants
  • 📦 Reproducible across any agent, team, or time
  • 🧭 Change is predictable — the spec is the ground truth
# spec: order-processing.yaml function: processOrder inputs: - name: orderId type: UUID - name: items type: Item[] min: 1 invariants: - total > 0 - all items in stock outputs: - confirmation: OrderConfirmation
The Process

How Spec Driven Development works

Five steps that transform ambiguous intent into deterministic, agent-ready systems. Click each step to expand.

1
Step 01

Write the Spec First

Before any code, before any prompt — write what the system must do.

A spec is a precise, machine-readable description of behavior. It answers: what are the inputs? outputs? invariants? edge cases? side effects? It doesn't say how — only what. Write it in YAML, Markdown, or a structured format your agents can parse. This is the single source of truth that every downstream step references.
2
Step 02

Generate Tests from the Spec

Tests aren't written after the fact — they're derived directly from spec invariants.

Each invariant in the spec becomes a test assertion. Each edge case becomes a test scenario. Because tests come from the spec — not from reading the code — they catch intent violations, not just implementation bugs. You can automate this with agents: feed the spec, get a test suite back.
3
Step 03

Implement Against the Spec

Pass the spec (not just a vague prompt) to your AI agent or developer.

With a spec in hand, an AI coding agent has unambiguous context. It knows exactly what to build, what to validate, and what failure looks like. There's no room for hallucinated assumptions. The implementation is constrained by the spec — not the agent's best guess at what you probably meant.
4
Step 04

Validate Against Invariants

Run the spec-derived tests. Any failure points back to the spec, not to intuition.

When tests fail, the spec tells you exactly which invariant was violated. This is debugging with precision — not archaeology. You know what broke, why it's wrong (the spec says so), and what correct behavior looks like. Fix the implementation or revise the spec — both are explicit decisions.
5
Step 05

Evolve Specs, Not Just Code

When requirements change, update the spec. Everything else follows.

In vibe coding, requirements drift silently. In SDD, every change is a spec change first. Update the spec → regenerate/update tests → update implementation. The diff in the spec file is the changelog. Agents can be re-run against the new spec without any human re-explanation. This is what makes agentic engineering composable and repeatable.
Core Tenets

The six principles of SDD

These aren't just best practices. They're the load-bearing walls of agentic engineering. Click each to learn more.

01
📋

Spec is the Source of Truth

The spec outranks the code, the tests, and memory. When they conflict, fix the spec first.

In a spec-driven system, the spec is the authoritative description of intent. If your code passes tests but violates the spec, your tests are wrong. Every agent, every developer, every reviewer reads the same spec.
02
🎯

Precision over Intuition

Ambiguity is technical debt. Every undefined behavior is a future bug waiting to happen.

Vague intent produces vague output. When you write "it should handle errors gracefully," you've written nothing. A spec says: "on input validation failure, return status 422 with a typed error payload". Agents can implement that. They can't implement vibes.
03
🤖

Agent-First Design

Design your specs to be consumed by machines, not just read by humans.

Specs should be structured, parseable, and self-contained. An AI agent should be able to pick up a spec cold and produce a correct implementation without any additional context. If it can't, the spec is incomplete.
04
🔗

Traceability

Every test, every implementation decision traces back to a spec statement.

If you can't point to the spec line that justifies a line of code, that code is unspecified behavior — a liability. Full traceability means every artifact in your system is grounded in explicit, reviewable intent.
05
♻️

Composability

Specs compose. Small, precise specs combine into larger systems without friction.

SDD enables modular, reusable system design. A spec for authentication composes with a spec for authorization. An agent that understands one spec can be orchestrated into a pipeline because every interface is explicit.
06
🔄

Continuous Alignment

Specs stay alive. They are maintained, versioned, and reviewed like production code.

A spec that gets out of date is worse than no spec — it's misleading. Version your specs, review spec changes as seriously as code changes, and automate spec validation in CI. The spec's health is the system's health.

# Feature Spec: User Login Version: 1.2.0 | Status: Approved | Owner: auth-team ## Purpose Authenticate a registered user with email + password and return a short-lived JWT. All auth events are audited. ## Inputs | Field | Type | Rules | |----------|--------|--------------------------------| | email | string | required, valid email format | | password | string | required, min 8 chars | ## Success Response — 200 { token: string (JWT), expiresAt: ISO8601 } ## Error Responses | Code | Status | Trigger | |----------|--------|--------------------------| | AUTH_001 | 401 | Wrong email or password | | AUTH_002 | 422 | Malformed input | | AUTH_003 | 429 | >5 failed attempts / min | ## Invariants (MUST hold at all times) - [ ] Passwords stored as bcrypt hash (cost ≥ 12) - [ ] Failed attempts rate-limited after 5 tries / minute - [ ] Token TTL ≤ 24 hours - [ ] p95 response time < 400ms ## Side Effects - Emit auth.login.success or auth.login.failed event - Write row to audit_log table on every attempt
// spec/auth/login.contract.ts // TypeScript contract — machine-readable, type-safe spec interface LoginInput { email: Email; // validated email string password: MinLen<8>; // minimum 8 characters } type LoginOutput = | { status: 200; token: JWT; expiresAt: ISODate } | { status: 401; code: "AUTH_001" } | { status: 422; code: "AUTH_002"; fields: string[] } | { status: 429; code: "AUTH_003"; retryAfter: number }; const LoginSpec = { invariants: [ "password stored as bcrypt, cost >= 12", "rate limit: 5 failed attempts per minute", "token TTL <= 86400 seconds", "p95 response time < 400ms", ], sideEffects: [ "emit: auth.login.success | auth.login.failed", "write: audit_log (every attempt)", ], } as const; // Agent receives this contract → generates tests → implements export type { LoginInput, LoginOutput }; export { LoginSpec };
